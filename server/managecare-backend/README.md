# ManageCare backend (custom Express + Postgres)

This is the live backend for the ManageCare app, deployed on the Hostinger VPS
at `/opt/managecare-backend/` (PM2-managed as `managecare-backend`, port 3000,
publicly reachable at `https://backend.managecare.info`).

It hand-implements a subset of the Supabase API surface (`/auth/v1/*`,
`/rest/v1/:table`, `/rest/v1/rpc/*`) so the Flutter app's `supabase_flutter`
client can talk to it, backed by the VPS's native PostgreSQL instance
(`managecare` database) instead of a real Supabase/GoTrue/PostgREST stack.

## Not tracked here

- `.env` — real secrets, never commit. See `.env.example` conventions used
  elsewhere in this repo; ask for the current values via the VPS directly.
- `node_modules/`
- `firestore-postgres-import.sql` — the Firebase data export/import script.
  Contains real business/customer data; this repo is public. Keep on the VPS
  only, or in a private, access-controlled backup location.
- `firestore-import-passwords.csv` — if this ever gets generated by a
  migration script, it must never be committed (plaintext credentials).
- `backups_*/` and `*.bak_*` — timestamped snapshots taken before deploying
  changes, VPS-local only.

## Deploying changes

There is no CI/CD pipeline yet. Changes are made locally, tested with
`node --check`, then copied to the VPS via `scp` and the service restarted
with `pm2 delete managecare-backend && pm2 start server.js --name
managecare-backend` (not `pm2 restart`, which does not reload environment
variables or pick up require()'d file changes in some cases — always prefer
delete+start for anything beyond a trivial code tweak).

## Security model

Unlike real Supabase (which enforces access via Postgres Row Level Security
policies, transparent to the API layer), this backend has **no RLS** —
authorization is enforced entirely in the Express middleware layer:

- `middleware/auth.js`: `authMiddleware` (verifies the JWT), 
  `requireBusinessMembership` (caller must be an active member of the
  business in the URL), `requireBusinessOwner` (caller must be the owner).
- Every business-scoped route file (`routes/*.js`) applies
  `requireBusinessMembership` at the router level via
  `router.use('/:businessId', requireBusinessMembership(pool))`.
- The generic `/rest/v1/:table` layer in `server.js` (`restAuthorize`)
  applies the equivalent per-table, since it doesn't have per-route URL
  params to hook into.

If you add a new business-scoped table or route, it must go through one of
these checks — there is no database-level fallback protecting it.
